# キーバインド設計

## グローバルホットキーとは

**OS 全体で有効なキーボードショートカット**のことです。
「グローバル」は「自分のアプリが最前面にいなくても反応する」という意味です。

通常のショートカット（⌘S など）は、そのアプリがアクティブなときしか効きません。
グローバルホットキーは、Safari を使っていても Xcode を使っていても、押した瞬間に反応します。

身近な例:

- **Spotlight** — ⌘Space
- **Raycast / Alfred** — ⌥Space など
- **画面収録** — ⇧⌘5

qool では **「他のアプリで作業している最中に、設定したキーを押すとメモが出てきて、
もう一度押すと引っ込む」** という部分がこれにあたります。

これがないと「Dock から起動して、ウィンドウを探して、クリックして…」という導線になり、
**思いついた瞬間に開く**という体験が成立しません。だから [MVP](mvp.md#mvp-のゴール) の要件に入っています。

## 要件

- **ユーザーが好きなキーの組み合わせを設定できること**
  （固定のキーを決め打ちにはしない。他アプリのショートカットと衝突するため）
- **ホットキー設定 UI の見た目を qool 側で作れること**
  ライブラリが用意する既製 UI を、そのまま置くしかない状態は不可

## 方針: プレフィックスキー方式

**`⌃Q` をプレフィックス（リーダーキー）とし、続けて押したキーで操作を決めます。**

```text
⌃Q → F    メインのメモを表示 / 非表示（トグル）
⌃Q → N    新しいメモを作る
⌃Q → …    以降、機能追加に応じて割り当てる
```

初期設定であり、**プレフィックス自体も各操作のキーもユーザーが変更できる**ようにします。

### なぜプレフィックス方式か

- **OS 全体に予約するホットキーが `⌃Q` の 1 つで済む**。
  操作ごとに `⌃⌥⌘F` のような組み合わせを個別に予約すると、機能追加のたびに
  他アプリとの衝突を探す必要が出てきます
- **名前空間が広い**。2 打目に使えるキーがほぼ全部空いているため、
  覚えやすい頭文字（F = flash? / N = new）を割り当てられます
- tmux の `⌃B`、Emacs の `⌃X` と同じ考え方で、**ユーザーにとって既知のパターン**です

## 実装上の重要な注意

### 「⌃Q + F の同時押し」は登録できない

グローバルホットキーの登録 API（Carbon `RegisterEventHotKey`）が受け取れるのは
**「修飾キー（Control / Option / Command / Shift）の組み合わせ + 通常キー 1 つ」**です。

`Q` も `F` も修飾キーではない通常キーなので、
**`⌃Q` と `F` を同時に押す形のホットキーは登録できません。**

したがって実装は **2 ストローク（⌃Q を押して離す → F を押す）** になります。
体感としては「⌃Q を押しながら F」に近い操作になりますが、内部的には別物です。

### 2 打目をどう受け取るか

`⌃Q` が発火した時点で、qool は最前面にいません。
その状態で次のキーを受け取る方法は 2 つあります。

| 方法 | 評価 |
|------|------|
| CGEvent tap / グローバルモニタでキーを監視 | **アクセシビリティ権限の許可がユーザーに必要**。初回起動のハードルが上がる |
| **小さなオーバーレイパネルを出して key window にする** | **権限不要。推奨** |

推奨は後者です。`⌃Q` を受けたら
`.nonactivatingPanel` スタイルの小さな透明パネルを表示して key window にし、
そのパネルが次の `keyDown` を受け取ってから閉じます。
Raycast や Alfred が呼び出し時にやっていることと同じ形で、特別な権限が要りません。

### プレフィックス中の挙動

- **ヒント表示**: パネルに割り当て一覧（`F 表示 / N 新規 …`）を出す。
  Vim の which-key のように、覚えていなくても使える状態にする
- **タイムアウト**: 数秒（1〜2 秒程度）で自動的に抜ける。押しっぱなしで固まらないようにする
- **キャンセル**: `Esc` で抜ける
- **未割り当てキー**: 何もせず抜ける

### `⌃Q` を選ぶときの注意

`⌃Q` はターミナルのフロー制御（XON、`⌃S` で止めた出力の再開）に使われています。
qool が `⌃Q` を OS 全体で奪うと、**ターミナル内で `⌃Q` が効かなくなります。**

ターミナルを日常的に使う環境では実害が出る可能性があるため、

- 初期値は `⌃Q` とするが、**変更できることを設定画面で明示する**
- あるいは初期値自体を別の組み合わせにする

のどちらかを決める必要があります（未確定）。

## メインのメモの表示 / 非表示

`⌃Q → F` の挙動です。

- 押すと**メインのメモ**が[任意形状のフローティングウィンドウ](../image-editing/04-integration-plan.md#48-mvp-のコアとして移植するもの)として表示される
- **もう一度押すと消える**（トグル）
- 表示位置とサイズは前回の状態を復元する

### 未確定: 「メイン」とは何か

決める必要があります。

| 案 | 内容 |
|----|------|
| ユーザーが指定 | メモ一覧で「メインにする」を選べる。明示的で分かりやすい |
| 直近に編集したメモ | 設定不要。ただし意図せず切り替わる |
| 固定の 1 枚 | 最初に作ったメモを常にメインとする。単純だが融通が利かない |

### 未確定: メイン以外のメモ

- メイン以外のメモも呼び出せるようにするか（`⌃Q → 数字` など）
- 複数のメモを同時に表示できるようにするか

MVP ではメイン 1 枚のトグルができれば要件を満たします。

## キーマップ（初期案）

| キー | 操作 | 状態 |
|------|------|------|
| `F` | メインのメモを表示 / 非表示 | MVP 対象 |
| `N` | 新しいメモを作る | MVP 対象 |
| — | 以降は機能追加に応じて | 未定 |

## 設定の永続化

ユーザーが変更したキー割り当ては保存する必要があります。
メモ本体とは性質が違う（小さく、単一で、頻繁に読まない）ため、
`UserDefaults`、またはホットキーライブラリが提供する保存機構に任せるのが素直です
（[永続化の方式](../architecture/persistence.md)の対象外）。

## 実装方式の候補

| 方式 | 内容 |
|------|------|
| Carbon `RegisterEventHotKey` | 古い C の API だが、グローバルホットキーでは今も事実上の標準。**特別な権限が不要**で、キーイベントを他のアプリに渡さずに奪える |
| `NSEvent.addGlobalMonitorForEvents` | Swift / AppKit で書けるが、**監視しかできずイベントを消費できない**（押したキーが裏のアプリにも届く）。加えてアクセシビリティ権限の許可が必要 |
| ライブラリ | 上記をラップしたもの。キー設定の記録 UI が付属するものもある |

`NSEvent` のグローバルモニタは、押したキーが裏のアプリにも流れてしまうため、
**呼び出し用のホットキーには向きません。** 実質的には Carbon 系の一択で、
問題は「それを自前で書くか、ライブラリに任せるか」になります。

## ライブラリを使う場合の判断軸

**「ホットキーの登録・解除の仕組み」と「キーを記録する UI」が分離しているか**を見ます。
分離していれば、ライブラリはエンジンとしてだけ使い、UI は qool 側で作れます。

| ライブラリ | 記録 UI | UI を自作できるか |
|------------|---------|-------------------|
| [`KeyboardShortcuts`](https://github.com/sindresorhus/KeyboardShortcuts) (Sindre Sorhus) | あり（SwiftUI / AppKit のレコーダー） | **可能**。ショートカットをコードから取得・設定できるため、レコーダーを使わず自作 UI から操作できる |
| [`HotKey`](https://github.com/soffes/HotKey) (soffes) | **なし** | 必然的に自作。Carbon の薄いラッパーで、機能はホットキー登録のみ |
| `MASShortcut` | あり | Objective-C 時代の定番。上 2 つに比べると新しい選択肢とは言いにくい |

**付属 UI をそのまま使うのが前提のライブラリだけは避ける**、というのが判断基準です。
`KeyboardShortcuts` と `HotKey` はどちらもこの条件を満たします。

いずれも着手時に、現行バージョンでの API とメンテナンス状況を確認してください。

## ライブラリ選定への影響

プレフィックス方式では、**ライブラリに求めるものが減ります。**

- OS へ登録するホットキーは `⌃Q` の 1 つだけ
- 2 打目はオーバーレイパネル内の通常のキーイベント処理

そのため「1 つのホットキーを確実に登録・解除でき、ユーザーが変更できる」ことだけが要件です。
[判断軸](#ライブラリを使う場合の判断軸)で挙げた `KeyboardShortcuts` / `HotKey` は
どちらもこれを満たします。

2 打目の割り当て UI は qool 側で自作することになります（プレフィックス方式に対応した
既製 UI を持つライブラリは期待できないため）。

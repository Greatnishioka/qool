# 永続化の方式（案）

**ステータス: 方式は A（ファイル + JSON）で決定。** 細部の未確定事項は[決めること](#決めること)を参照。

現状のリポジトリ実装は [`InMemoryMemoRepository`](../../qool/Infrastructure/Persistence/InMemoryMemoRepository.swift) だけで、
アプリを終了すると内容が消えます。[MVP](../product/mvp.md#mvp-のゴール) の
「作ったメモをホットキーで呼び出す」は永続化なしには成立しないため、**MVP の必須要素**です。
方式は決まったので、あとは実装するだけの状態です。

## 保存する必要があるもの

| 対象 | 性質 |
|------|------|
| `Memo`（タイトル / 更新日時 / `Canvas`） | 小さい構造化データ。数 KB 程度 |
| `CanvasElement` の配列 | 図形の形状・色・テキスト・Union の構成元スナップショット |
| 切り抜きの元画像 | **大きいバイナリ**。写真なら 1 枚数 MB |
| 切り抜き輪郭・調整パラメータ | 小さい。元画像と組で意味を持つ |
| ウィンドウの位置・サイズ | メモごとの表示状態 |

**構造化データと大きなバイナリが混在する**のが、この題材の性質です。

## 前提となっている設計

現在のドメインモデルは**すべて値型（`struct`）で、`Equatable` / `Hashable`** です。

```swift
struct Memo: Identifiable, Equatable, Hashable {
    let id: UUID
    var title: String
    var updatedAt: Date
    var canvas: Canvas
}
```

この形は `Codable` を付けるだけでシリアライズできます。
一方で、参照型（クラス）を前提とする永続化フレームワークとは相性が悪く、変換層が必要になります。

また `MemoRepository` という protocol がすでに切られているため、
**どの方式を選んでも後から差し替えられます。** 最初の選択に過度な重みはありません。

## 選択肢

### A. ファイル（JSON + 画像ファイル）

メモ 1 件 = 1 ディレクトリ。メタデータは JSON、画像は素のファイルとして置く。

- **利点**
  - 既存の `struct` に `Codable` を付けるだけで済む。**ドメインモデルを変えなくてよい**
  - Domain がフレームワークに依存しない（[アーキテクチャ方針](mvvm-clean-architecture.md#レイヤごとの責務)と一致）
  - 画像が最初からファイルなので、DB に巨大な BLOB を入れる問題が起きない
  - 中身を Finder / エディタで直接見られる。壊れたときに手で直せる
  - **スキーマを変えたら消してやり直せる**。[クラッシュアンドビルド方針](../product/mvp.md#開発方針)と相性がよい
- **欠点**
  - 検索・並べ替え・絞り込みは自前実装
  - 起動時に全メモを読む素朴な実装だと、件数が増えたときに遅くなる
  - マイグレーションは自前（JSON にスキーマバージョンを持たせる）
  - 書き込み中のクラッシュ対策（アトミック書き込み）を自分で担保する必要がある

### B. SwiftData

- **利点**
  - macOS 14+ の標準。マイグレーション機構がある
  - SwiftUI との統合（`@Query` による自動更新）
- **欠点**
  - `@Model` は**参照型（クラス）**が前提。現在の値型ドメインモデルと形が合わない
  - 方針どおり Infrastructure に SwiftData 用のモデルを置いて相互変換すると、
    **SwiftData の旨味（自動監視・`@Query`）がほぼ消えて、ボイラープレートだけが残る**
  - 逆にドメインモデルを `@Model` クラスにすると、**Domain が SwiftData に依存**しレイヤが崩れる
  - 大きな画像バイナリの扱いは結局 external storage 頼みで、ファイル方式と大差ない
  - 比較的新しく、入れ子の値型配列を多く持つモデルでは扱いに注意が要る

### C. Core Data

- **利点**: 枯れている。マイグレーションが強力。大規模でも性能が出る
- **欠点**: ボイラープレートが多い。値型との変換層が必須。**MVP には明らかに過剰**

### D. 単一ドキュメントファイル（`.qool` パッケージ）

メモ 1 件 = `NSFileWrapper` による 1 パッケージ。ドキュメントベースアプリの形。

- **利点**: 書き出し・共有・バックアップが自然。将来の [PDF 書き出し](../product/mvp.md#mvp-のスコープ外将来検討)とも相性がよい
- **欠点**: qool は「メモ一覧を持つ常駐アプリ」なので、ドキュメントベースの体験とは噛み合わない。
  ただし **A の内部構造をそのままパッケージ化すれば、後から D に寄せられます**（[独自拡張子](#独自拡張子qool)）

## 推奨: A（ファイル + JSON）

MVP を早く立ち上げる観点では、理由は 3 点です。

1. **ドメインモデルを一切変えずに済む**。`Codable` を足すだけ
2. **アーキテクチャ方針を守れる**。Domain がフレームワークに依存しない
3. **作り直しに強い**。スキーマを変えたらディレクトリごと消せばよい

## 長期で見ても A がよいか

**「MVP だから簡単な方を選ぶ」ではなく、長期的にどれが最適かを別途評価します。**

結論から言うと、**この題材では長期的にも A が最適**だと考えます。
速さのための妥協ではなく、データの形に合っているためです。

### データの形が「文書」であって「関係」ではない

永続化フレームワークが本領を発揮するのは、**エンティティ同士に関係があり、
それをまたぐ問い合わせが必要な場合**です。qool のデータはそうなっていません。

- 実際のアクセスパターンは **「一覧をメタデータだけで出す」「1 件を開いて丸ごと描画する」** の 2 つだけ
- メモ同士に関係がない。結合も集計も要らない
- 主な容量を占めるのは画像バイナリで、これは DB が得意なものではない

**1 メモ = 1 ディレクトリ**という構成は、このアクセスパターンにそのまま対応します。

### 壊れたときの被害範囲

Core Data / SwiftData のストアが壊れると、**全メモを一度に失う**可能性があります。
ファイル方式なら、壊れるのは該当する 1 メモのディレクトリだけです。

個人が長年ためていくメモという性質上、この差は小さくありません。

### 外部ツールと組み合わせられる

- Time Machine や Git でバージョン管理できる
- Finder でコピー・移動・バックアップできる
- 中身を直接見て手で直せる

不透明なバイナリストアでは、どれもできません。**個人用ツールとしては実利のある差**です。

### 将来機能との相性

| 将来機能 | ファイル方式での見通し |
|----------|----------------------|
| [PDF 書き出し](../product/mvp.md#mvp-のスコープ外将来検討) | 1 メモ = 1 ディレクトリなので素直に対応する |
| [Markdown](../product/mvp.md#mvp-のスコープ外将来検討) | 同上。テキストをファイルとして持つのは自然 |
| 全文検索 | **ファイル単体では弱い。** 下記の折衷案で対応する |
| 同期 | **ここだけは DB 方式が有利**（下記） |

### 折衷案: ファイルを正とし、索引は派生物にする

将来メモが増えて全文検索が要るようになったら、
**ファイルを唯一の正とし、そこから生成する SQLite の索引を別に置く**構成にします。

```text
memos/                  ← 正。これさえあれば復元できる
index.sqlite            ← 派生物。消しても memos/ から作り直せる
```

こうすると検索性能を得ながら、「壊れても復元できる」「外部ツールで扱える」という
ファイル方式の利点を保てます。**索引を正データにしないことが要点です。**

### 反対意見として認めるべき点

**同期が必要になった場合、この判断は不利に働きます。**

- SwiftData / Core Data は CloudKit との統合が用意されており、同期を後付けしやすい
- ファイル方式でも iCloud Drive（`NSFileCoordinator`）で実現できますが、
  競合解決を自分で書く必要があります
- ファイルから DB への移行は、後からやると相応の作業量になります

現時点で [同期はスコープ外](../product/mvp.md#mvp-のスコープ外将来検討)であり、
[macOS 専用](../product/mvp.md#決定プラットフォーム-macos-専用)と決まったことで
マルチデバイス同期の必然性も下がっています。
**同期が主要要件になった時点で、設計ごと見直す前提**でよいと考えます。

なお `MemoRepository` の protocol があるため、差し替え自体の影響範囲は限定されます。

### 結論

| 条件 | 最適 |
|------|------|
| **qool の想定（個人用・画像中心・macOS 専用・同期なし）** | **A（ファイル）** |
| 数千件規模 + タグや関連付け + 横断検索が中心 | Core Data / SwiftData |
| マルチデバイス同期が主要要件 | SwiftData + CloudKit |

qool は 1 行目に当てはまります。

### レイアウト案

```text
~/Library/Application Support/qool/
  memos/
    <memo-uuid>/
      memo.json          Memo + Canvas + CanvasElement（schemaVersion を持たせる）
      window.json        ウィンドウ位置・サイズ
      assets/
        <asset-uuid>.png       切り抜きの元画像（下記参照）
        <asset-uuid>.cache.png 表示用にレンダリング済みの切り抜き（再生成可能）
  index.json             一覧表示用の軽量メタデータ（タイトル / 更新日時 / 要素数）
```

- `index.json` があると、**一覧表示のために全メモの JSON を開かずに済みます**。
  一覧は起動直後に必要で、キャンバスの中身は開いたときに初めて要るためです
- `.cache.png` は消えても再生成できる位置づけにしておく

## 画像アセットの持ち方

**ここが設計上いちばん重要な判断です。**

### 何を「正」として保存するか

切り抜き済みの画像だけを保存すると、**後から輪郭を修正できなくなります。**
StarWindow は `editedContour`（編集後の輪郭）を設定として保持する作りになっており、
これを保存しておけば再編集の余地が残ります。

したがって保存するのは:

- **元画像**（正）
- **輪郭**（`pathContours` / `editedContour` 相当。正）
- **調整パラメータ**（不透明度・明度・余白・ぼかし。正）
- 切り抜き結果（**キャッシュ**。上の 3 つからいつでも再生成できる）

### 元画像のサイズ対策

元の写真をそのまま抱えると、メモ 1 枚あたり数 MB になります。
**輪郭の bounding box に余白を付けてクロップしたものを「元画像」として保存する**と、
再編集の余地を残しつつサイズを抑えられます。
余白の量は、後から輪郭を広げ直せる程度（StarWindow の
`displayRangeEditingPreviewMarginPixels` = 48px が目安）。

### モデル側の持ち方

`CanvasElement` に `NSImage` を直接持たせては**いけません**。
`Memo` は `Equatable` / `Hashable` な値型で、`CanvasViewModel` の `@Published var memo` は
編集のたびに丸ごとコピー・比較されます。ここに画像が入ると、
図形を 1px 動かすたびに画像のコピーと比較が走ります。

```swift
// Domain: ID だけを持つ
var imageAssetID: UUID?

// Domain: protocol
protocol ImageAssetRepository {
    func image(for id: UUID) -> NSImage?
    func save(_ image: NSImage) -> UUID
    func delete(id: UUID)
}
```

実体の解決は Infrastructure の実装が担い、Presentation はキャッシュ経由で受け取ります。

### 同一画像の重複

同じ写真から複数のメモを作った場合、素朴に実装すると元画像が重複します。
コンテンツハッシュで共有する手もありますが、**MVP では重複を許容してよい**と考えます
（共有すると削除時の参照カウントが必要になり、複雑さが増えるため）。

## 独自拡張子（`.qool`）

**使えます。** しかも推奨案 A のレイアウト（1 メモ = 1 ディレクトリ）とは相性が良く、
構造を変えずに導入できます。

### 2 つの形式

macOS で独自拡張子を扱う場合、中身の持ち方に 2 通りあります。

| 形式 | 実体 | 向き |
|------|------|------|
| **フラットファイル** | 1 つのファイル。中身は独自形式や zip | 単一のバイナリで完結する場合 |
| **パッケージ（バンドル）** | **実体はディレクトリだが、Finder では 1 ファイルに見える** | **複数のファイルで構成される場合。qool はこちら** |

qool のメモは「JSON + 複数の画像ファイル」で構成されるため、**パッケージ形式が適切**です。
`.app` や `.rtfd` と同じ仕組みで、ディレクトリのまま扱いながら、
ユーザーには 1 つのファイルとして見せられます。

### 推奨案 A からの移行コストがほぼない

[レイアウト案](#レイアウト案)はすでに「1 メモ = 1 ディレクトリ」です。
これをパッケージにするのに必要なのは実質 2 つだけです。

```text
memos/<memo-uuid>/          →   memos/<名前>.qool/
                                  memo.json
                                  window.json
                                  assets/
```

1. ディレクトリ名に `.qool` を付ける
2. Info.plist で UTI を宣言する

**内部構造は一切変えなくて済みます。**

### 必要な宣言

- **UTI（Uniform Type Identifier）を exported type として宣言する**
  - 識別子は逆 DNS 形式（例: `dev.ayato.qool.memo`）
  - `public.data` ではなく **`com.apple.package` に conform させる**（パッケージ形式の場合）
  - 拡張子（`qool`）とアイコンを紐づける
- **`CFBundleDocumentTypes`** で、その UTI を qool が開けることを宣言する
- コード側は `UTType` として参照し、読み書きは `NSFileWrapper` を使う
  （**パッケージ全体をアトミックに書き込める**ため、書き込み中のクラッシュに強くなります）

### 拡張子名の注意

- 拡張子は中央管理されていないため、**他アプリとの衝突は原理的にありうる**（実用上は問題になりにくい）
- UTI 識別子は自分のドメインを使った逆 DNS にして、こちらは確実に一意にする
- 短く、小文字で、覚えやすいものにする。`.qool` はこの条件を満たす

### トレードオフ: 中身が見えにくくなる

[ファイル方式の利点](#外部ツールと組み合わせられる)として「Finder で中身を直接見られる」を挙げましたが、
パッケージにすると Finder では 1 ファイルに見えるため、
**中を覗くのに「パッケージの内容を表示」の一手間が要ります。**

実体はディレクトリのままなので、Time Machine・Git・`cd` での操作には影響しません。
失われるのは Finder でのダブルクリック閲覧だけです。

### どこに置くかは別の判断

独自拡張子を導入すると、**ドキュメント型アプリ**（ユーザーが好きな場所にファイルを置く）に
寄せたくなりますが、これは別の判断です。

| 方式 | 内容 |
|------|------|
| **ライブラリ管理型** | `~/Library/Application Support/qool/` にアプリが管理。ユーザーはファイルの存在を意識しない |
| ドキュメント型 | ユーザーが保存先を選ぶ。`⌘S` で保存、Finder からダブルクリックで開く |

**推奨はライブラリ管理型です。** qool は
[ホットキーで呼び出して使うアプリ](../product/hotkeys.md)であり、
「思いついた瞬間に開く」体験にファイル管理の手間は不要だからです。

その上で **`.qool` パッケージを「書き出し / 読み込み」の形式として用意する**のが良い形です。

- 通常はアプリが `~/Library/Application Support/qool/` で管理する
- メモを他の Mac へ移したい、バックアップしたい、共有したいときに `.qool` として書き出す
- 受け取った `.qool` をダブルクリックすると qool に取り込まれる

これなら、日常の体験を単純に保ちながら、可搬性も得られます。
